# ai-coding

> 一个把「AI 编码」从随缘对话变成**有纪律的工程流程**的 Skill。
> 让 AI 按「先分析需求 → 澄清 → 再编码 → 四维度自审」干活，而不是拿到一句话就开始瞎写。

---

## 它解决什么问题

用 AI 写代码，几乎都会遇到这四种情况：

| 现象 | 根因 |
|---|---|
| 代码框架对，业务逻辑空着或写错 | AI 不了解你的业务上下文 |
| 代码乱放，破坏分层 | AI 不了解你的工程结构 |
| 规范只存在老员工脑子里 | 隐性知识没显性化，AI 读不到 |
| 产量上来了，质量下滑 | 缺适配 AI 的质量保障机制 |

对应解法只有一句话：

> **把架构和规范从人脑里抠出来，写成文件，做成 AI 能自动加载的资产。**

本 skill 用三个组件实现这件事：

| 组件 | 类比 | 承载内容 | 加载方式 |
|---|---|---|---|
| **宪法 Rules** | 宪法 | 架构模式、目录结构、技术栈、编码风格、红线 | Always 生效 |
| **规范 Spec** | 法规 | 需求分析 / 编码 / CR 各环节规范 | 按需加载 |
| **流程 Skills** | 执法机构 | 四阶段闭环，自动识别意图并执行 | 语义自动触发 |

## 我在此基础上做了什么

原演讲讲的是**思路**，没有可直接使用的成品；公开发布的实录里也**没有字段级模板和真实目录树**。本项目的增量主要在三处：

### 1. 工程化封装为可安装的 Skill
原分享是一套团队内部实践，没有分发形态。本项目把它打包成符合
[skills](https://skills.sh) 生态规范的 Skill，一行命令即可安装，跨 agent 可用。

### 2. 补齐了缺失的字段级模板（主要工作量）
原分享只说明"要有需求分析模板、编码规范、CR 标准"，未给出内容。本项目独立撰写：

- `references/constitution-template.md` —— 项目宪法模板（架构/目录/技术栈/风格/红线）
- `references/requirement-templates.md` —— 新增类 / 修改类两套需求分析模板
- `references/coding-standards.md` —— 后端分层 + 前端组件规范，附自检清单
- `references/review-rubric.md` —— 四维度评分表、评分锚点、闭环规则

### 3. 按「变更频率」重新拆分三层资产
这是相比原方案最容易落地的一点改进。原实践需要把整套规范拷进每个项目，本项目改为：

| 资产 | 变更频率 | 放在哪 |
|---|---|---|
| 流程（四阶段） | 几乎不变 | **Skill 本体** — 装一次，全局可用 |
| 规范模板 | 偶尔优化 | **Skill 的 `references/`** — 改一次处处生效 |
| 宪法（架构/红线） | 每个项目都不同 | **项目根 `CLAUDE.md`** — 由阶段 0 自动生成 |

结果：**项目里只留一个 `CLAUDE.md` 和产出目录 `.ai/docs/`**，不需要往每个项目拷模板。

此外还补充了：四阶段意图路由表、五条铁律、概念纪律（功能点≠用例）、反模式清单。

## 安装

### 方式 1：任何支持 skills 的 agent（推荐）

```bash
npx skills@latest add <你的用户名>/ai-coding
```

指定 agent：

```bash
npx skills@latest add <你的用户名>/ai-coding -a cursor -a claude-code
```

### 方式 2：CodeBuddy —— 拷目录

```bash
git clone https://github.com/<你的用户名>/ai-coding.git /tmp/ai-coding
cp -R /tmp/ai-coding/skills/ai-coding ~/.codebuddy/skills/
```

项目级（随仓库提交给团队）：

```bash
mkdir -p .codebuddy/skills && cp -R /tmp/ai-coding/skills/ai-coding .codebuddy/skills/
```

### 方式 3：手动 —— 解压 `dist/ai-coding.zip`

把 `ai-coding/` 放进 `~/.codebuddy/skills/` 即可。

**装完重启会话。**

## 怎么用

Skill 靠**语义自动触发**，不需要敲 `/ai-coding`：

| 场景 | 你说 | AI 自动进入 |
|---|---|---|
| 首次在某项目用 | 「分析当前工程结构，生成 CLAUDE.md」 | 阶段 0：产出项目宪法 |
| 来了个新需求 | 「分析下这个需求」+ 贴需求 | 阶段 1→2：需求文档 + 待澄清清单 |
| 需求澄清完 | 「帮我实现编码」 | 阶段 3：拆任务 → 实现 → 出 DDL/接口文档 |
| 写完了 | 「做一次 code review」 | 阶段 4：四维度打分 → 自修 → 迭代 3~5 轮 |

**唯一的操作纪律**：阶段 2 的待澄清问题，**攒齐一次性回**，不要来回挤牙膏。

## 能达到什么效果

### 原作者团队的实测数据（60+ 人，2025.4–9）

| 指标 | 数值 |
|---|---|
| AI 编码率 | 9% → **89.2%**（9 倍+） |
| 千行代码 bug 率 | **< 0.2** |
| 发布回滚率 | **< 2%** |
| 极端案例 | 66 文件 / 5000+ 行，全程只说了一次「继续」 |
| CR 评分 | 70 → **96 分**，本地编译一次通过 |

> 注意：这是**原作者团队**的数据，不是本项目的。本项目只是把方法封装成可直接使用的形态。

### 个人 / 小团队的合理预期

| 阶段 | 效果 |
|---|---|
| 第 1 周 | AI 不再"乱写乱放"；歧义在需求阶段一次性问清，少 2~3 轮返工 |
| 第 1 个月 | 单需求做到"一次生成 + 3~5 轮自审收敛"；CR 有统一标准 |
| 第 3 个月 | 规范越积越厚，同类错误被逐条"回改规范"消灭 |

### 三个前提（否则达不到）

1. **需求真能澄清** —— 需求本身没想清楚时，模板只会把糊涂放大
2. **出错回改规范，不是只改代码** —— 这是复利的唯一来源
3. **人不能撤** —— 跨应用需求边界仍需人工界定，最终 Review 责任在人
