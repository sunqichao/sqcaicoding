# 交付归档与基座回写

> 阶段 5 使用。目标：每次交付后把知识**回流成资产**，让下一次 AI 起点更高（资产飞轮）。
> 适用：L / XL 必做，M 可选，S 跳过。**归档由 AI 生成、人确认**，人只需几分钟。

---

## 一、为什么要做

- 没有归档，线上出问题时只能重新翻代码、问人，排查成本高
- 对话里学到的约定、术语、踩坑，不写回基座，下一次 AI 仍会重犯
- CI 只能检查"代码 ↔ 代码"，**"代码 ↔ 需求 / 设计"是否仍一致，需要在此环节显式核对**

---

## 二、产出物：`.ai/docs/<需求名>/99-release.md`

```markdown
# 交付归档：<需求名>

## 1. 变更摘要
- 做了什么（一两句话）；对应需求文件：01-requirement.md

## 2. Diff 分类
| 类别 | 文件 / 模块 | 说明 |
|---|---|---|
| 业务逻辑 | | |
| 接口 / 契约 | | |
| 数据结构（DDL） | | |
| 公共能力（被多处依赖） | | |
| 配置 / 其他 | | |

## 3. 公共能力影响
- 改动了哪些公共模块 / 共享组件；引用方清单；兼容性结论

## 4. 验证覆盖
- 验收标准 → 对应测试 / 验证步骤 → 结果
- 最终 CR 评分与轮次；是否为独立验证

## 5. 遗留风险与待办
- 已知风险、非阻塞假设中**尚未被人确认**的项、技术债（只记录，不在本次处理）

## 6. 回写记录
- 本次回写了哪些基座内容（见下节），或"无需回写"
```

---

## 三、一致性核对（回写前）

逐项核对，发现不一致**显式列出，不默默修正**：

- 需求中的每个功能点与验收标准，代码是否都实现了？（未实现 / 超出需求）
- 接口 / 数据结构的最终形态，是否与 `01-requirement.md`、接口文档一致？不一致处以代码实际行为为准，并**同步更新文档**
- 非阻塞假设是否已被人确认？未确认的写入遗留风险

---

## 四、基座回写

**回写对象**：宪法文件（`AGENTS.md`）与 `.ai/docs/` 下的项目级基座文档。

**可回写的内容**（只写**可复用、会长期成立**的事实）：
- 新增或变更的架构约定、分层规则、红线
- 新出现的术语及定义
- 新增的公共组件 / 工具及使用方式
- 本次踩到的坑，以及"以后该怎么做"

**不回写**：一次性的业务细节、临时方案、尚未确认的假设。

**流程**：
1. 逐条列出"拟回写内容 + 目标文件 + 具体 diff"
2. **等人确认后才写入**；人拒绝的条目不得再次静默写入
3. 若某条问题的根因是 skill 规范缺失，回改 `references/*.md`（与铁律 3 一致）

---

## 五、追加式变更日志（可选）

在 `.ai/docs/RELEASE-LOG.md` **只追加**一行：

```
| 日期 | 需求名 | 级别 | 一句话摘要 | 归档链接 |
```

只追加、不改写，便于追溯。
