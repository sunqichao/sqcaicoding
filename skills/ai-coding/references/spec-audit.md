# 存量 Spec 盘点规范

> 阶段 0.5 使用。目标：把项目里**散落、重复、过期、与代码脱节**的需求文档整理成可用资产。
> 原则：**只读不删、不替用户判断业务价值、冲突必须显式呈现。**

---

## 一、发现：扫描范围

按优先级扫描，命中即记录：

| 位置 | 说明 |
|---|---|
| `.ai/docs/` | 本方案的历史产出 |
| `docs/` / `doc/` | 常见文档目录 |
| `specs/` / `requirements/` / `design/` / `prd/` | 需求/设计专用目录 |
| `openspec/` / `.specify/` / `.kiro/` | SDD 工具的产物 |
| 根目录 `*.md` | 排除 `README.md`、`CHANGELOG.md`、`LICENSE.md`、`CONTRIBUTING.md` |
| issue tracker 导出 | 若用户提供，一并纳入 |
| `CLAUDE.md` / `AGENTS.md` / `.trae/rules/` | 这些是宪法不是 spec，但其中可能夹带需求描述，需摘出 |

---

## 二、分类：每份文档打三个标签

### 标签 1：类型
- **需求**（what / why）—— 用户要什么
- **技术方案**（how）—— 怎么实现
- **决策记录 ADR** —— 为什么这么选
- **过程产物** —— 评审记录、排期、会议纪要
- **混合** —— 需求与方案揉在一起（最常见，需拆分）

### 标签 2：状态
- **有效** —— 与当前代码一致
- **部分过期** —— 主体有效，局部与代码不符
- **已过期** —— 描述的功能已下线或被替代
- **未实现** —— 只存在于文档，代码里没有
- **重复** —— 与其他文档描述同一件事

### 标签 3：质量问题
- 缺验收标准
- 缺前置条件 / 业务规则
- 功能点与用例混淆（"删除门店" vs "成功删除"）
- 术语与宪法不一致
- 无负责人 / 无日期

---

## 三、交叉核对（本阶段最有价值的部分）

对每份"需求"类文档，与代码和宪法三方比对，产出三类事实：

| 类型 | 判定 | 输出 |
|---|---|---|
| **未实现** | 文档有、代码无 | 列出功能点，标注是否仍需要 |
| **未记录** | 代码有、文档无 | 列出模块，提示补文档 |
| **冲突** | 文档描述 ≠ 代码行为 | **以代码实际行为为准**，但必须显式写明分歧点 |

> 冲突不要静默修正。写清楚"文档说 A，代码做的是 B"，让用户决定哪个是对的。

| 主题 | 涉及文档 | 建议 |

| 宪法用词 | 文档中的其他写法 | 出现位置 |

| 文档 | 动作 | 理由 | 目标位置 |

## 五、执行纪律

1. **只读不删**：盘点阶段不改动、不删除原文件；重写时也保留原文件
2. **不替用户判断业务价值**：不写"这个没用了建议删"，只写"距最后修改 18 个月、代码中未找到对应实现"
3. **冲突必须暴露**：不允许自动"统一"成某一种说法
4. **分两批交付**：先给盘点报告让人确认，再执行重写。不要一次做到底
5. **重写时统一术语**：以项目宪法（`AGENTS.md` 等）的用词为准，不一致处先问
