# 需求分析模板

> 阶段 1 使用。**核心设计**：新增类与修改类走两套模板——新增侧重整体架构设计，修改侧重对现有代码的影响分析。
> 产出写入 `.ai/docs/<需求名>/01-requirement.md`。

---

## 零、铁律（最高优先级）

1. **禁止猜测**：任何不清楚、有歧义、缺条件之处，必须集中列入"待澄清列表"，等待人工确认
2. 推断必须显式标注为待确认项，不得伪装成结论
3. 存在**阻塞项**时，不得进入编码阶段；非阻塞项必须写成显式假设，不得默默带过
4. 阻塞判定：答案不同会导致数据模型 / 接口契约 / 权限 / 金额逻辑 / 状态机不同，或事后回退代价高；拿不准按阻塞处理
5. 全程使用工程既有术语，**禁止自创新词**

## 一、新增类需求

> 适用：从零建设，不依赖或不改动现有代码。

```markdown
# 需求：<名称>（类型：新增）

## 1. 需求功能清单
- [ ] 功能点 1
- [ ] 功能点 2

## 2. 模块详细分析
对每个功能点说明：
- 前置条件
- 业务流程（主流程 + 分支）
- 业务规则
- 涉及的模块与边界
- 数据流向
- 接口契约（入参 / 出参 / 错误码语义，不写具体文件路径）
- **验收标准**（可验证：给定什么输入 → 预期什么结果；含至少一个异常 / 边界场景）

## 3. 待澄清列表
| # | 问题 | 影响 | 类型（阻塞 / 非阻塞） | 我的倾向 |
|---|---|---|---|---|
| 1 | TODO | TODO | TODO | TODO |

## 4. 假设（仅非阻塞项）
| # | 假设内容 | 对应待澄清项 | 回改代价 |
|---|---|---|---|
```

## 三、输出要求

- 采用**结构化**而非散文，便于后续逐条勾稽
- 不写具体文件路径与代码片段（易过时）
- 涉及表结构变更时，本阶段只给**变更意图**，DDL 留到阶段 3 产出
- 完成后提示用户："待澄清清单已生成，请一次性回复所有问题"
- **M 级（精简需求）**只保留：功能清单 + 验收标准 + 待澄清列表，其余可省略
