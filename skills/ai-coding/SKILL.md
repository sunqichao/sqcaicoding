# AI Coding 纪律化流程

## 目的

把架构与规范从人脑里显性化，用**宪法约束 AI**，而不是继续用规范约束人。
目标不是"写得更快"，而是**一次交付对的东西**，并且同类错误只犯一次。

## 三层资产的职责边界（不要混）

| 层 | 位置 | 内容 | 维护方式 |
|---|---|---|---|
| **宪法 Rules** | 项目根，文件名随工具（见下方工具适配矩阵） | 架构模式、目录结构、技术栈、编码风格、红线 | 每项目一份，由阶段 0 生成，人工维护 |
| **规范 Spec** | 本 skill 的 `references/` | 需求分析模板、编码规范、CR 评分标准 | 全局共享，改一次处处生效 |
| **流程 Skill** | 本文件 | 四阶段路由与执行纪律 | 本 skill |

**关键约束：不要把模板拷进项目。** 模板留在 skill 的 `references/`，项目里只留宪法文件和 `.ai/docs/` 产出物。

### 工具适配矩阵（决定宪法写到哪里）

不同 AI 开发工具读的规则文件路径不同。始终以 **`AGENTS.md` 为主文件**（已被 Claude Code v2.1.277+、GitHub Copilot、Trae 等直接读取），其余工具放**一行指针**，避免多份内容不一致。

| 工具 | 读取路径 | 写入策略 |
|---|---|---|
| **AGENTS.md（跨工具标准）** | `AGENTS.md` | **主文件，写全量内容** |
| Claude Code / CodeBuddy | `CLAUDE.md` | 指针：`@AGENTS.md` |
| Trae | `.trae/rules/project_rules.md`（该目录下所有 `.md` 均 always-applied） | 指针：首行写"完整工程宪法见项目根 AGENTS.md，执行任何任务前先读取" |
| Cursor | `.cursor/rules/*.mdc` 或 `.cursorrules` | 指针（同上） |
| Windsurf | `.windsurf/rules/*.md` | 指针（同上） |
| GitHub Copilot | `.github/copilot-instructions.md`，也读 `AGENTS.md` | 通常无需额外文件 |
| Gemini CLI | `GEMINI.md` | 指针（同上） |

**决策规则**：
- 用户只用一个工具 → 直接写该工具的原生文件名，可以不放 `AGENTS.md`
- 用户混用多个工具 → `AGENTS.md` 写全量，其他工具只放指针
- 无法确定工具 → 默认只写 `AGENTS.md`，并告知用户如何按需补指针

生成前先检测工程里已存在的规则目录/文件（`.trae/`、`.cursor/`、`.cursorrules`、`CLAUDE.md`、`AGENTS.md`、`.windsurf/`、`.github/copilot-instructions.md`、`GEMINI.md`），据此判断用户实际在用什么工具，**不要凭空假设**。

## 阶段路由

先判断用户处在哪个阶段，再执行对应流程。

| 意图信号 | 进入 | 必读 |
|---|---|---|
| 首次在某工程使用 / "梳理架构" / "生成 CLAUDE.md / AGENTS.md" | 阶段 0 | `references/constitution-template.md` |
| 项目里已有大量文档 / "梳理已有 spec" / "盘点需求文档" / "整理历史 PRD" / "文档和代码对不上" | 阶段 0.5 | `references/spec-audit.md` |
| 贴需求、PRD、"分析需求"、"做技术方案" | 阶段 1 → 2 | `references/requirement-templates.md` |
| "开始实现"、"写代码"、"按需求做" | 阶段 3 | `references/coding-standards.md` + 项目宪法文件 |
| "code review"、"审查"、"检查代码质量" | 阶段 4 | `references/review-rubric.md` |

无法判断时：读项目宪法文件（`AGENTS.md` / `CLAUDE.md` / `.trae/rules/` 等）与 `.ai/docs/` 现有产物，据此推断阶段。

## 阶段 0：接入工程（每个工程一次）

1. **检测用户在用哪些工具**：检查 `.trae/`、`.cursor/`、`.cursorrules`、`CLAUDE.md`、`AGENTS.md`、`.windsurf/`、`.github/copilot-instructions.md`、`GEMINI.md` 是否存在，据工具适配矩阵决定写入位置
2. 读 `references/constitution-template.md`
3. 扫描工程，产出四项：架构模式、目录结构、技术栈及版本、编码风格（附证据：哪些目录体现了该模式）
4. 标注**偏差**：实际代码哪里已偏离它本该遵循的结构（越层调用、职责跑偏、循环依赖）
5. 呈现给用户确认，**不直接覆盖已有宪法文件**；同时告知"我准备写到 X 路径"，让用户可以选择只写某一个工具
6. 确认后写入。`TODO` 项留给用户补充
7. 若写入了多个工具的文件，明确告知各文件的**主从关系**（以 `AGENTS.md` 为准），避免以后只改一份造成不一致

不做任何代码改动。

## 阶段 0.5：存量 Spec 盘点（可选分支）

> 触发：用户说"梳理/盘点/整理已有的 spec""需求文档太乱""现有文档和代码对不上"。
> 适用：项目里已散落着 PRD、技术方案、OpenSpec 的 changes/、issue、历史 `.ai/docs/`，需要统一。

1. 读 `references/spec-audit.md`
2. **发现**：扫描所有可能的 spec 位置，列出清单（路径、类型、最后修改时间、篇幅）
   - `docs/`、`doc/`、`specs/`、`requirements/`、`design/`、`.ai/docs/`、`openspec/`
   - 根目录散落的 `*.md`（排除 README / CHANGELOG / LICENSE）
   - 已有的 `CLAUDE.md` / `AGENTS.md` / `.trae/rules/` 里的约束条款
3. **分类**：逐份判断是 需求（what/why）/ 技术方案（how）/ 决策记录 ADR / 已过期 / 重复冲突
4. **与代码和宪法交叉核对**，找出三类事实：
   - 文档里有、代码里没有 → 未实现
   - 代码里有、文档里没有 → 未记录
   - 文档与代码描述不一致 → 冲突（**以代码实际行为为准，但要显式标注**）
5. **输出盘点报告** → `.ai/docs/_spec-audit.md`（格式见 reference）
6. **给迁移建议**：保留 / 合并 / 重写 / 归档 / 废弃，逐项列理由
7. 用户确认后才按新模板重写；**重写时保留原文件**，不删除

**本阶段铁律**：
- **只读不删**：盘点期间不改动、不删除任何原文件
- **不替用户判断业务价值**：只陈述事实（不一致、重复、过期迹象），去留由人决定
- 冲突处不要默默"修正"，要让用户看见分歧

## 阶段 1：需求分析

1. 读 `references/requirement-templates.md`
2. **先判断需求类型**（本阶段核心动作）：
   - 新增类（从零建设，不改存量代码）→ 侧重整体架构设计
   - 修改类（改动存量代码）→ 侧重影响分析
   - 混合型：主类型走对应模板，另一侧作为附注
3. 按模板产出，写入 `.ai/docs/<需求名>/01-requirement.md`
4. 必须产出**待澄清列表**

## 阶段 2：需求澄清

1. 把所有不确定项**集中一次性**呈现给用户
2. 禁止逐轮挤牙膏提问（每轮分析 2~3 分钟，批量提问效率高一个数量级）
3. **待澄清列表非空时，禁止进入阶段 3**

## 阶段 3：编码实现

1. 确认 `01-requirement.md` 的待澄清列表为空
2. **先拆子任务并记录状态**（防上下文爆掉，中断可恢复）；拆分顺序从底层数据层到上层应用层
3. 严格落在 `CLAUDE.md` 定义的分层与目录内
4. 不留 `TODO`、不留空实现、不假装完成
5. **同步产出过程文件**：DDL 脚本、接口文档 → `.ai/docs/<需求名>/`
6. 走 `references/coding-standards.md` 末尾的自检清单，在回复中给出勾选结果

## 阶段 4：审查 → 优化闭环

1. 读 `references/review-rubric.md`
2. 四维度审查并打分：功能逻辑 / 代码设计 / 代码质量 / 代码规范
3. 输出报告：总分 + 严重问题 + 一般问题 + **高风险提示**（留给人工终审）
4. **立刻按严重问题自行修改**，改完重新自审，迭代 3~5 轮，目标 ≥95 分
5. 连续两轮无提升 → 停止并上报人工
6. 若问题源于**规范缺失**，回改 `references/*.md`，不要只改代码

## 铁律

1. **禁止猜测**：不清楚的必须列入待澄清列表等人工确认，不允许"合理推断"后直接开写
2. **规范里不放业务逻辑**，否则无法跨项目复用
3. **出错回改规范**，同类错误只犯一次——这是整套方法复利的来源
4. **人保留终审权**：跨应用需求边界、高风险逻辑由人裁定
5. **不降低标准换分数**：CR 不得通过删需求、改评分锚点来"提高"得分

## 概念纪律

- **功能点 ≠ 用例**："删除门店"是一个功能点；"成功删除""取消删除"是它的两个用例
- 禁止把一个需求拆成多个 spec 文件散落各处
- 编码粒度有 7 级（行 / 块 / 函数 / 类 / 模块 / 项目 / 工程），越往上效率越高质量越不可控，**不要一上来追求工程级**

## 反模式（出现即纠正）

- 需求没澄清就开始写代码
- 把模板复制进项目（应留在 skill 的 `references/`）
- CR 只出报告不修代码
- 代码出错只改代码、不回改规范
- 修改类需求顺手重构无关代码
